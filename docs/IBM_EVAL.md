## 1. What was done

* **Ingest** (`ingest/ibm.py`): 5,078,345 source rows; 591,212 self-transfers dropped (11 of them labelled laundering; 0 account(s) were laundering only through a self-transfer and so leave the truth set). 30,528 IBM bank ids → 5 simulated banks by SHA-256 of the id (all accounts of one IBM bank stay together). Each transaction → one OUT row at the sender's bank and one IN row at the receiver's bank: 8,974,266 canonical rows, 422,734 accounts. Own account = `client_id` `<ibm bank>:<account>`; the counterparty is only an external token of the same form (like an IBAN).
* **Amounts**: Amount Paid × a hand-typed **PLACEHOLDER** USD table (`config/ibm.yaml`, `placeholder: true`). See §6 for its deviation from the rates implied by the dataset itself.
* **Labels** (`Is Laundering`, pattern types) are split off before the bank split and read only by the metric code in `eval/ibm_eval.py`; `bank_split` refuses a labelled table (unit test). Account truth = sender or receiver of ≥ 1 laundering transaction. Pattern types: 3,209 lines of the patterns file, 3,209 matched to transactions on (timestamp, both accounts, amount, currency, format), 370 attempts. Laundering accounts not covered by the patterns file are reported as `unattributed`.
* **Bank-side engine** (own design, IBM-scale vectorised variant of D1 flow-through+ / D5 rare-exit concentration; polars, no python loop per client): per own account inside ONE node — counterparty degree within the node, in/out totals and counts, max 24 h inflow window, share of the largest inflow sent on within 24 h (to others than its payer), share of outflow to rare counterparties (degree ≤ 3 within the node), distinct rare counterparties, retention, and a second pass with the max first-pass probability of counterparties that are the node's OWN clients. Score = additive log-odds with **hand-set** weights (no fitting):

| weight | value |
|---|---|
| `bias` | -7.0 |
| `drain_24h` | 2.0 |
| `flow_ratio` | 1.5 |
| `low_retention` | 0.5 |
| `rare_out_share` | 1.0 |
| `log_n_rare_cp` | 0.5 |
| `log_deg_in` | 0.5 |
| `log10_max_in_24h` | 0.15 |
| `neighbour` | 2.0 |

* **Split / threshold** (the only use of labels for a choice): labels of the calibration window are used for exactly one choice (the flag threshold); weights are hand-set; the held-out window was never used for any choice; 'full' contains the calibration days and is labelled so. Calibration window 2022-09-01 … < 2022-09-10; threshold grid = 306 score quantiles; chosen logit threshold **-2.9369** (calibration F1 0.0464, P 0.0248, R 0.3647, 78,604 of 419,212 accounts flagged; calibration AP 0.0268). Features are computed only from rows inside each window.
* **Radar** (`staj_psi`): candidate band = score ≥ threshold − 1.5 (weakly suspicious included, never all accounts); per candidate the top 4 counterparty tokens by amount with in-bank degree ≤ 3; at most 1500 tokens per bank (highest scores first; measured PSI cost in this run: 13.59 ms per token per pair session, 300 tokens per side). Admission by `radar.guards.Guards` (config from `config/thresholds.yaml`); every bank pair runs `radar.sessions.run_radar` (real `PsiParty` DH-PSI) in its own process; the coordinator unions the per-pair matches and calls `radar.clustering.build_clusters` once (same connected components as one all-bank run). Disclosure needs ≥ 2 banks and ≥ 3 candidates. Each bank maps its own `cand_ref`s in disclosed clusters back to accounts and adds 2.0 logit points; a flag is never removed. The post-match lag/retention exchange (§6.4 'same hand global') is **not** used on IBM.
* **naive_raw_sharing**: all canonical rows pooled into one node, same engine (global counterparty degree, neighbours across banks). Exposure = all rows; bytes = parquet serialisation.
* **Baselines** on the same accounts: top-k by transaction count, by distinct counterparties, seeded random (k = number flagged by `isolated`). An **evaluation-only** logistic regression fitted on calibration labels over the same features is reported as a reference, never used for a flag.

## 4. Honest assessment

* **The bank-side engine is weak on AMLworld.** Held-out AP 0.037 vs prevalence 0.0088 (×4.2); full-period AP 0.0309 vs prevalence 0.01504 (×2.1). F1 at the calibrated threshold: 0.0425 held-out, 0.0541 full. The F1-optimal threshold flags 6.9 % (held-out) and 18.9 % (full) of all accounts: **not a usable alert volume**. A one-line baseline, distinct counterparties, reaches AP 0.0407 (held-out) and 0.0379 (full), i.e. it is higher than the isolated engine on the held-out window and higher than it on the full period.
* The evaluation-only logistic fit on the same features reaches held-out AP 0.0711 (×1.9 the hand-set engine) and P@1000 0.175: the hand-set weights leave signal on the table, but even fitted these features stay far from a usable detector.
* **Radar, held-out**: 18 disclosed clusters, 36 of 63 boosted accounts are laundering. Ranking effect: AP 0.037 → 0.0509 (lifted), P@100 0.31 → 0.47; boosted-account precision 0.571 vs flag precision 0.024. The radar adds 0 new flags: the boosted accounts were already above the threshold, so precision/recall/F1 do not change. 3.8 % of the submitted candidates are laundering accounts.
* **Radar, full**: 4 disclosed clusters, 1 of 12 boosted accounts are laundering. Ranking effect: AP 0.0309 → 0.0309 (no lift), P@100 0.19 → 0.2; boosted-account precision 0.083 vs flag precision 0.0292. The radar adds 0 new flags: the boosted accounts were already above the threshold, so precision/recall/F1 do not change. 5.5 % of the submitted candidates are laundering accounts.
* **naive_raw_sharing is not an upper bound** with this engine: F1 0.0374 vs isolated 0.0425 (held-out), 0.0531 vs 0.0541 (full). Pooling changes counterparty degrees (fewer tokens count as 'rare') and lets the neighbour pass see every account. It exposes 8,974,266 rows (117,787,452 bytes as parquet) over the full period; staj_psi exposes 0 raw records and 15,360,000 bytes of blinded group elements.
* **Pattern types (held-out, isolated)**: best account recall cycle 0.7558, random 0.5789; worst bipartite 0.0843, fan-in 0.1161, gather-scatter 0.1254. Pass-through members (e.g. of cycles) look like flow-through accounts and are found more often. The most-missed accounts are the patterns' endpoints: pure senders (n_in = 0, e.g. fan-out and scatter-gather sources) and pure receivers (n_out = 0, e.g. fan-in sinks), for which every flow-through feature is 0 (see the missed-accounts tables). Token matching on shared counterparties cannot link a chain across banks (consecutive hops share no counterparty); submitting the candidate's OWN account token would, but discloses more and was not evaluated.
* **Worst false positives** (full period): 4 of the top 8 have a neighbour score ≥ 0.9 (groups of mutually high-scoring accounts inside one simulated bank reinforce each other through the neighbour pass); 8 of 8 send ≥ 95 % of their largest inflow on within 24 h, ≥ 95 % of outflow to rare counterparties. Under these features they are indistinguishable from mules; that is a weakness of the features and of the second pass.
* The held-out window is unusual: 2022-09-10 is a partial day and 2022-09-11 … 09-18 hold only 1,108 rows, 655 of them laundering (tail of attempts). Features see only rows inside the window, so held-out accounts have at most ~9 days of history.

## 4b. Deviations from the design brief (and why)

1. **Split**: the brief allows 'report on the later days'. Days 10–18 hold only 204,649 of 4,487,133 non-self transactions, so the full period is reported as well, labelled as containing the calibration days.
2. **PSI orchestration**: one `run_radar` over all 5 banks runs its 10 pair sessions sequentially (~325 s of PSI summed over pairs in the full window). Each pair therefore calls `run_radar` on that pair in its own process, and the coordinator re-clusters the union with `build_clusters` (identical connected components, unit-tested on a 3-bank example). Token budget 1500 per bank, kept below `radar.psi.dh_psi.PARALLEL_MIN` so the per-pair processes do not start nested process pools. Note: `radar/psi/dh_psi.py` was changed by another engineer during this work (256-bit secret exponents, Jacobi-symbol subgroup check, optional process pool); the numbers here come from the version on disk at generation time, and the per-run benchmark above is the measured cost.
3. **Accounts**: the source has 515,088 accounts; 92,354 of them appear only in self-transfers, which are dropped, leaving 422,734. Laundering accounts lost that way: 0.
4. **Patterns file** lines matched to 3,209 laundering transactions; laundering accounts outside the file are reported as `unattributed`.
5. **Post-match lag/retention exchange** ('same hand global') is not used on IBM; it would add disclosure without a tested benefit here.

## 5. Limitations (exact)

1. Synthetic data; generic AMLworld laundering patterns, **not** Czech mule schemes; results say nothing about real portfolios.
2. FX is a hand-typed **placeholder** table (approximate public rates); it differs from the dataset's own implied rates (§6). Amounts enter only ratios and log-materiality.
3. Weights are hand-set; only the flag threshold was chosen on calibration labels (days 1–9). The engine design (D1/D5 features) predates this run; the payment-format/label crosstab was seen during data exploration and payment format is deliberately NOT a feature.
4. The simulated bank split is a hash of IBM bank ids; real banks differ in size and customer mix.
5. The radar is limited by DH-PSI cost and the token budget: 387–411 candidates per bank enter PSI (full period) out of 27,852–37,602 in the band, so most of the band never enters PSI. Pair sessions run in parallel processes on one laptop; nodes are not separate machines.
6. Security model is semi-honest. A malicious bank could submit arbitrary tokens to probe whether an account is a candidate elsewhere, inject fake tokens to create or enlarge clusters (poisoning), or abort after learning its result. Mitigations in this code: Guards (minimum set size, max tokens, rate limit, share of unscored tokens), disclosure only for ≥ 2 banks and ≥ 3 candidates, only keyed token ids reach the coordinator, humans decide. Not mitigated: a bank that scores fake accounts to pass the 'scored' check, collusion of two banks, traffic analysis by the coordinator. PSI minimises disclosure; it is **not a legal basis** for sharing.
7. `naive_raw_sharing` is a privacy-exposure reference, not a detection upper bound.
